Episode 03

Deployment with an AI agent

Afaf Arfaoui · November 17, 2026

In episode 02 we deployed two microVMs by hand: upf-uvm, which will host the eUPF, and agent-uvm, which will host the monitoring agent, both connected through a bridge with NAT. Every step was done and checked manually, so we know what a correct deployment looks like.

In this episode, we hand that same deployment to an AI agent. We build it piece by piece: the scripts it is allowed to run, the loop that connects it to the model, the instructions it receives, and the approval, log, and saved state that keep it under control. We then run it under supervision, first as a dry run and then for real, and compare the result with the deployment we built by hand.

The goal is to test whether an AI agent can carry out an infrastructure deployment safely: we decide what it may run, we approve every change to the machine, and we can see and stop everything it does.

1. What we automate

The deployment itself does not change. The agent carries out the same stages as in episode 02, in the same order: checking the machine, fetching the Firecracker release, the kernel and the root filesystem, building the network and the disks, starting the two microVMs, and checking that both answer.

What changes is how they are run. We turn each stage into a script, and the agent can run these scripts and nothing else. We build them in this episode:

ScriptWhat it does
check-prereqs.shChecks the machine: architecture, /dev/kvm access, required tools, free disk space, default route, and whether Firecracker is installed. Changes nothing.
fetch-artifacts.shDownloads the Firecracker release, the CI kernel, and the Ubuntu rootfs into the lab folder. Files that already exist are skipped.
host-network.shCreates or removes the bridge, the TAP devices, and NAT, and shows their status.
build-rootfs.shBuilds the disk for one microVM from the Ubuntu image, with its SSH key and DNS settings.
vm.shStarts, stops, or shows the status of one microVM.
health.shChecks that a microVM answers and that you can log in to it.
teardown.shRemoves the lab in the reverse order it was built.
