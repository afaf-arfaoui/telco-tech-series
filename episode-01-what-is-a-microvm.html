MicroVMs in theory

Dr. Afaf Arfaoui · September 11, 2026 · …

1. Introduction

The best way to grasp the concept of microVMs is to familiarize ourselves with the two technologies it sits between, which are conventional Virtual Machines (VMs) and containers. This is because microVM is not completely invented from scratch, rather, it is a VM that uses the same hardware virtualization foundations as a conventional VM, but with nearly all non-essential features removed. The outcome is a virtualization technology that, from a security standpoint, operates like a full VM, yet exhibits speed and density close to that of containers.

In this episode we will walk through the background of how VMs and containers function under the hood (starting with the layered view in Fig. 1 below), the reason behind the creation of microVMs, and how a microVM virtualizes CPU, memory and I/O, which, as we will see, differs far less from a conventional VM than one might expect. We can then compare the three virtualization methods and list the benefits and drawbacks of microVMs specifically. At the end of the episode we will be discovering existing microVM solutions.

2. Background
How does a traditional VM work?

A conventional VM, the kind hosted by a hypervisor platform such as VMware ESXi, Xen, QEMU+KVM, or Hyper-V, relies on hardware-assisted virtualization. What does it mean? It means using CPU extensions such as VT-x (Intel) and AMD-V that let a CPU run virtual machines more efficiently. These extensions enable the CPU core to switch, for most guest execution, into a distinct hardware execution mode for running guest code: Intel terms this VMX non-root operation, and AMD terms it guest mode. This document uses "guest mode" to refer to either. Within guest mode, the guest operating system keeps its normal internal separation between kernel-level and user-level code, exactly as it would on physical hardware. A hardware boundary is drawn around the entire guest, kernel included: certain operations, no matter which part of the guest performs them, are flagged by the CPU as requiring the host's attention. These operations are described under VM exits below and illustrated in Fig. 2.

A hardware boundary surrounds the entire guest, kernel included, regardless of what runs inside it.

Beyond running guest instructions natively, two further hardware features are what make the VM model both safe and practical:

  • Extended/Nested Page Tables (EPT/NPT): Normally, CPU memory management unit translates virtual addresses to physical addresses using page tables. In a VM, there is an extra layer: guest virtual address → guest physical address→ host physical address. EPT/NPT lets the CPU perform that second translation in hardware. This is the actual security boundary between VMs: the CPU itself checks and translates the guest's memory accesses (see Fig. 3 below), ensuring the guest cannot access memory outside the region the hypervisor mapped for it, no matter what are its software actions. This hardware-enforced boundary is the most important fact for later understanding why VMs (and microVMs) are considered more isolated than containers.
  • VM exits/entries: Whenever the guest attempts something that the CPU is not able to carry out on its own, such as a privileged instruction, an I/O port access, or a timer interrupt meant for the host, the CPU exits guest mode into KVM (what is called a "VM exit"). The KVM role here is to set up and execute the actual hardware transition, and to decode why the exit happened. For most device-related exits, KVM does not emulate anything itself, it packages up the exit reason and hands control to the userspace VMM (e.g., QEMU), which is the piece that actually performs the emulation. KVM does resolve a small number of performance-critical cases entirely on its own, without ever involving the VMM, but that is not the general rule. What happens next depends on the cause of the exit. For an I/O port access, the VMM typically computes the value a real device would have produced and returns it. For a timer interrupt meant for the host, there is nothing to emulate, the host simply uses the moment to run its own scheduler, for example checking whether this vCPU's timeslice has expired. In either case, the guest resumes with a VM entry (see Fig. 2 below) and never becomes aware it was paused. Every VM exit still costs time, since leaving and re-entering guest mode is not free, which is a large part of why VMMs and microVM design focuses on minimizing how often it happens.

This traces one specific exit cause, an I/O port access, which KVM decodes and hands to the userspace VMM to emulate. A timer interrupt meant for the host would exit the same way but skip the EMULATE step entirely, proceeding directly to the host's own scheduling work before resuming the guest.

In Fig. 1, the stack reads bottom-up as "who talks with what"

  • The hardware exposes VT-x/AMD-V and EPT, discussed earlier, the CPU features that make guest mode execution and memory isolation enforced by the hardware possible
  • KVM (Kernel-based Virtual Machine) turns those raw CPU features into a usable interface, exposed to userspace as the special device file /dev/kvm: create a VM, create vCPUs, map guest memory.
  • The VMM (Virtual Machine Monitor) such as QEMU[1] (and later will see for microVM Firecracker[2], Cloud Hypervisor[3], etc.) is a userspace process that calls into that /dev/kvm interface via ioctls to create the VM, allocate its vCPUs (virtual CPUs) and hand over a region of its own memory to serve as the guest's RAM. It also performs the device emulation.
  • The guest VMs are vCPU threads inside the VMM process. Each of those threads spends most of its time executing guest instructions directly on the CPU in guest mode. It only comes back up through KVM to the VMM on a VM exit, then goes back (VM entry) to resume (refer to Fig. 2).

Hardware features like Intel VT-x or AMD-V cannot be used directly by programs in the userspace. Operations such as the following involve low-level and sensitive setup that needs to be managed by the kernel:

  • setting up EPT/NPT that translate guest physical addresses to host physical addresses and enforce the isolation boundary.
  • managing the VM entry/exit transitions that involve the CPU switching into and out of guest mode and saving and restoring the state each time.

The KVM module, in the kernel, packages these VT-x or AMD-V operations into a small set of defined commands, exposed through the special device file /dev/kvm. The VMM (QEMU, Firecracker, Cloud Hypervisor, or whichever userspace process is managing that VM) opens /dev/kvm and issues a sequence of ioctl() calls* to create a VM, create its vCPUs, and map a region of its own (i.e., VMM) memory to serve as the guest's physical RAM. That translation, from raw CPU virtualization features to a straightforward requests any userspace program can issue, is what makes /dev/kvm a usable interface.

* ioctl() calls are a standard Linux mechanism for sending commands to a device in the kernel[4].

Now that we understand the role of VMM, KVM, and features such as VT-x and AMD-V, the last point is to understand where the conventional VMs get heavy.

Because the guest OS expects to find a real PC underneath it, a conventional VMM emulates the complete legacy environment: BIOS, UEFI firmware, chipset, PCI bus, VGA adapter, keyboard controller, and USB controllers. Every time the guest touches one of these emulated devices, that access traps out as a VM exit, which the VMM then resolves by emulating the behavior the real hardware would have shown. Because of this full emulation, the guest boots the same way as a physical computer: the firmware runs, conducts a power-on self-test, transfers control to a bootloader (such as GRUB), which then loads the kernel that initializes every one of those emulated devices through its driver. This entire process highlights why a conventional VM may take several seconds to boot. A microVM does away with almost all of this: no firmware, no chipset, no PCI bus, no USB stack,etc., to emulate.

Something to keep in mind: conventional VMMs do not emulate all devices in this "slow" way. For devices that experience high traffic (e.g., network card or disk) it uses virtio[5] which is a paravirtualized interface that allows the guest to run a driver that knows it is actually communicating with the VMM rather than through registers designed to mimic hardware. Therefore a typical VM device model is a mix between legacy full emulation for rarely invoked hardware or critical operations, and virtio is used for whatever needs to move data fast. This mix matter for later: a microVM virtualization does not invent virtio, it just discards the legacy emulation and trims the remaining virtio side down to the bare minimum needed to boot and run.

To have a sense of scale: QEMU [1], the most widely used general-purpose VMM, is well over a million lines of code. This is what a purpose-built microVM VMM like Firecracker avoids. Firecracker's entire codebase, virtio devices, etc., comes in at tens of thousands of lines only [2].

How do containers work?

The mechanism of containers is completely different from that of VMs. Containers do not rely on hardware virtualization, instead they are regular processes running under the same kernel as the host (depicted in Fig. 4 below), but made to seem isolated using kernel features:

Fig. 4 · Container isolation: namespaces, cgroups and security mechanisms

Several Linux kernel mechanisms work together to produce this appearance of isolation, without any hardware virtualization involved:

  • Namespaces give a process its own private view of a particular system resource (e.g., network, filesystem, etc.), despite it executing under the same kernel as every other process on the host. A PID (Process ID) namespace, for instance, confines a process to its own process hierarchy, so that it sees only itself and its descendants while the host's other processes remain hidden. A network namespace likewise gives it its own interfaces, addresses and routing rules. A mount namespace presents it with its own filesystem view, distinct from the host's actual filesystem [6].
  • cgroups (control groups) impose quantitative limits on the resources (CPU time, memory, I/O bandwidth) available to a process or group of processes [7], which is what prevents any single container from monopolizing the host.
  • Security mechanisms add further constraints beyond namespaces and cgroups. Capabilities break the "all-or-nothing" root privilege into smaller, individually grantable permissions, while seccomp filters restrict which system calls a process is allowed to invoke from the kernel [8]. Finally, MAC (Mandatory Access Control) tools such as AppArmor or SELinux enforce policies, defined by the administrator, that determine which interactions a process may have with the resources it sees through its namespaces.

Because there is no firmware, device emulation, or separate kernel to boot, starting a container translates to just starting a process which takes milliseconds. Unlike a VM, there is no guest kernel or emulated firmware to load into memory before anything else can run. A container's memory footprint is simply whatever the application itself allocates, plus a thin runtime layer such as a small init process, rather than the tens to hundreds of megabytes a guest OS typically needs before the application inside it even starts.

Container isolation depends entirely on one shared kernel enforcing it correctly. A container receives the same hardware enforced memory protection that any process receives, namely its own address space via the CPU's page tables, but this is true for every process on the machine, whether containerized or not, and therefore does not by itself distinguish one tenant's container from another's. The isolation between containers, provided by namespaces, cgroups, capabilities, and seccomp, is instead software policy enforced by that single shared kernel. A virtual machine adds something a container does not have: a second, independent hardware check, provided by EPT or NPT, that operates beneath the guest's own kernel and constrains what that kernel can access, regardless of the kernel's own behavior. Consequently, if the shared host kernel underlying a set of containers contains a bug in its namespace or system call handling code, the mechanism enforcing the isolation boundary is itself compromised, with no further layer to fall back on.

A virtual machine has a second, independent hardware check beneath the guest's own kernel. A container has no equivalent second layer beneath the one kernel it shares with everyone else.
3. Why microVMs appeared?

That isolation gap between VMs and containers is not just a theoretical distinction. It became a real business constraint for one particular kind of workload. Cloud providers faced a very specific issue. For them to provide services such as FaaS (Functions-as-a-Service), they needed to run code from thousands of different customers, packed densely onto the same physical servers, and with new instances spinning up and down constantly (often for a few hundred milliseconds of execution) [1]. A concrete example of FaaS could be a small function that runs whenever another system sends it a webhook (i.e., a notification that one system sends automatically to another over the web the instant some event happens, rather than the second system having to repeatedly check whether anything has occurred). For example, a payment provider might send a webhook to a customer's function the moment a payment succeeds, carrying the details of that transaction, so the function can react immediately (e.g., updating an order's status). A Cloud provider runs this function only when such a notification is received. The function runs for a small period of time, e.g., ten to hundreds of milliseconds, then the Cloud provider terminates its instance. At any given moment, thousands of these short-lived functions, belonging to different customers, are being triggered and terminated in this same way, and all of them are sharing the same infrastructure. Fig. 5 illustrates this density and churn.

Fig. 5 · FaaS density and churn: many short-lived functions sharing the same hardware

This made it hard to satisfy two conflicting requirements:

  • Isolation: The function of customer A must never be able to read the memory or data of customer B's function, or affect its execution, even if customer function A is malicious. In this case, containers are considered insufficiently isolated for this multi-tenancy, precisely because of the shared-kernel risk described above. A related, more recent scenario is an AI agent that can execute arbitrary, model-generated code or shell commands on a user's behalf. If that execution is not isolated, the agent has the same reach as any other process on the host: it can read, modify, or delete anything the host process could touch, install software, or make outbound network connections, regardless of whether the model that generated those actions was manipulated, buggy, or simply mistaken. Running that execution inside a microVM confines it to its own kernel and its own hardware-enforced memory boundary, so a compromised or misbehaving agent cannot reach beyond the microVM it was given. This is a significant reason multiple AI infrastructure providers now run agent code execution this way.
  • Speed and density: a traditional VM per function invocation will be too slow to boot (it can take seconds when the whole function invocation might last milliseconds) and too heavy in memory (a full guest OS as well as a heavyweight VMM per instance) to run at the density and pace the business required.

AWS built internally a technology that satisfies these requirements to power Lambda and Fargate. It did release it as open source in 2018 under the name Firecracker which is considered as the project that popularized the term "microVM".

AWS was not alone in facing this trade-off. Separate motivation had already been building in the container world itself: projects like Intel's Clear Containers [9] and Hyper.sh's runV [10] had spent the preceding years experimenting with running each container inside a lightweight VM instead of a shared-kernel namespace, to get isolation closer to a VM's while keeping close to a container's efficiency. Those two projects merged in December 2017 to form Kata Containers [11] [12], about a year before Firecracker was open sourced.

Kata Containers is not a virtualization technology, it is a container runtime, the same category of software as runc, and in fact a replacement for it. It implements the OCI (Open Container Initiative) runtime interface, so Docker, containerd, Kubernetes, etc., can call it exactly the same way they would call runc, without being aware of the difference. Its job is to take the container image, decides how to run it, manages its lifecycle, and reports back through the same APIs a real container would use.

Instead of using namespaces and cgroups, Kata Containers runs each container inside an actual VM, which requires a VMM. That VMM is pluggable: Kata can be configured to use QEMU (a full, general-purpose VMM), or Cloud Hypervisor and Firecracker (a microVM VMM). This makes Kata Containers agnostic to whether a microVM is actually running underneath any given deployment. That is determined entirely by which VMM backend it is configured with. What Kata always provides, regardless of backend, is the layer that makes whatever VM is running underneath look and behave like an ordinary container to Kubernetes: injecting the container image into the VM, running a small in-guest agent that receives commands the way runc normally would on the host, and wiring up networking so the container looks completely normal from the outside.

In summary, Kata Containers is the integration layer that lets VM-based container isolation sit underneath an unmodified container ecosystem.

4. What is a MicroVM and how it works?

At its core a microVM is a VM, it uses KVM, real vCPUs, and EPT for hardware memory isolation, exactly as described in Section 2. What differs is the VMM. Instead of emulating a full generic PC, a microVM VMM implements only a few virtual devices actually needed, and skips the legacy PC boot sequence entirely. Concretely, this involves several specific engineering choices:

A minimal device model

Instead of the full legacy device set described in Section 2, a microVM VMM may expose, for example:

  • only one or two virtio devices (built on the paravirtualized mechanism introduced in Section 2) for networking and block storage
  • a virtio-vsock for host and guest communication
  • a bare serial console for logs.

This is very efficient since there is no need to emulate a specific real chip's hardware registers. In fact, the guest virtio driver communicates with the VMM through shared memory ring buffers called virtqueues. This means that the VMM does not have to reimplement, for instance, an Intel e1000 NIC register behavior, rather it just have to service a queue of requests. Fewer emulated registers = fewer possible VM exits + less code + smaller attack surface. The less code an attacker can target through a VM exit means fewer opportunities to exploit the VMM itself and reach the host.

Direct kernel boot

We recall from Section 2 that a traditional VM guest boots as if it were physical hardware (firmware → bootloader → kernel). A microVM VMM instead loads the guest kernel image directly into the guest memory itself, before the vCPU even starts, and sets the vCPU's initial instruction pointer straight to the kernel's entry point (following a documented boot protocol, e.g., the Linux kernel boot protocol). There is no BIOS POST, no bootloader reading from a virtual disk. This alone removes most of the seconds that a traditional VM spends before it is useful. MicroVMs can reach guest-kernel-running state in roughly 150ms [2] (see Fig. 5 and Section 5.4 of that reference).

The guest kernel itself is usually also trimmed for a specific purpose: a minimal config with unnecessary drivers, filesystems, etc., paired with a small, often statically-linked root filesystem. This reduces both boot time further and the amount of code running inside the guest that could itself contain vulnerabilities.

The mechanics of virtualizing each resource
  • CPU: the VMM asks KVM to create one or more vCPUs. Each vCPU is a host thread that enters guest mode and executes the guest's actual instructions directly on the physical core. It continues executing at native speed until something happens that the CPU cannot handle by itself (a privileged instruction, an emulated-device access, etc.), which causes a VM exit back into the VMM/KVM to handle the event, followed by a VM entry to resume the guest [13]. Because a microVM has so few emulated devices, VM exits happen far less often than in a fully-emulated VM, which is a major reason microVMs also have lower steady-state CPU overhead (Fig. 6, below, contrasts this with full hardware emulation).
  • Memory: the VMM allocates (mmap) a region of its own address space to serve as the guest's entire physical RAM, and registers that region with KVM (via a call like KVM_SET_USER_MEMORY_REGION) [14]. From that point, the CPU's EPT hardware sits underneath the guest's own page tables. The guest translates guest virtual addresses to guest physical addresses itself, exactly as it would on bare metal. EPT performs the next step, translating those guest physical addresses into host physical addresses. This is the actual isolation mechanism: it is enforced by the CPU's memory management hardware, not by a software check that a clever attacker might bypass. Most microVM VMMs require you to specify the memory size up front at creation time, though some support later resizing via memory ballooning
  • I/O (network/disk): handled entirely through virtio, the same mechanism a traditional VM uses for its network and disk, the difference being that in a microVM it is the only option, with no legacy emulation alongside it. For networking, the VMM connects a virtio-net device inside the guest to a TAP interface on the host, a virtual network interface that behaves like the guest's own network cable plugged into the host. The guest and the VMM exchange packets through a small shared memory queue instead of through emulated hardware registers, and a lightweight notification tells the VMM when new data is waiting, instead of the VMM having to check constantly. Storage works the same way: the guest describes what it wants to read or write, and the VMM turns that into an ordinary read or write against a file or block device on the host. In both cases, the VMM's role reduces to translating these queue requests into real host operations. It never has to imitate a specific NIC or disk controller chip.
Fig. 6 · Full emulation versus virtio: fewer, batched traps into the VMM

The notification mechanism mentioned above has a name. When the guest places a new descriptor in the virtqueue, it signals the VMM through a lightweight KVM mechanism called an ioeventfd [14], which resolves the notification inside the kernel and avoids a synchronous round trip into the userspace VMM for every packet. This is necessary because a guest simply writing to its own memory does not trigger anything on its own. Without an explicit signal, the VMM would have to poll the queue continuously to notice new work. Once the VMM has processed the request, for example forwarding a network packet through the TAP device, it signals completion back to the guest via a matching mechanism called an irqfd [14].

5. MicroVM vs. Traditional VM vs. Container

With the mechanics of all three established, the differences can be set side by side, as shown in Table 1. The essential thing to notice is that a microVM shares its isolation column with the traditional VM and its speed column with the container. That combination is the entire reason it exists.

Device model Full emulated PC (BIOS, PCI, VGA, USB…) None: just host syscalls Minimal: a few virtio devices only
Boot path Firmware → bootloader → kernel None, the process just starts directly Kernel loaded directly by the VMM

Memory overhead per instance High (guest OS + heavy VMM) Very low (just the app) Low (trimmed OS + tiny VMM)
VMM / runtime code size Large (e.g., QEMU: over a million lines) Not applicable Small (tens of thousands of lines)

6. Benefits and disadvantages of MicroVMs

The tradeoffs below follow directly from the mechanism described in the previous sections. The benefits stem largely from the same hardware boundary and minimal device model already discussed. The limitations stem mostly from how young the microVM ecosystem still is relative to decades-old hypervisor platforms and the container ecosystem.

Benefits
Hardware-enforced isolation between tenants
without paying the full cost of a traditional VM. This is the core value proposition: it is safe to run code you do not trust, belonging to customers who do not trust each other [2].
Fast startup
which makes workloads like serverless functions viable, where a cold start must complete in well under a second [2].
Small attack surface
A minimal device model and a compact, often memory-safe VMM codebase leave fewer places for exploitable defects to hide, and fewer VM exits for an attacker to abuse even where one exists [2][15].
Low overhead per instance
relative to a full VM, permitting far higher density: many more isolated sandboxes on the same physical host [2].
Per-tenant kernel flexibility
Because each microVM runs its own kernel, different tenants can run different kernel versions or configurations side by side.
Compatibility with existing ecosystems
Through projects such as Kata Containers, microVMs can serve as a VM-isolated backend for standard container tooling, so the isolation upgrade does not require abandoning the container workflow [12].
Disadvantages and limitations
Still heavier than a container
Each microVM needs its own kernel resident in memory and its own boot sequence, however fast. A plain container remains lighter and quicker to start, being merely a host process.
Limited device support
The minimal device model that makes microVMs fast and secure also constrains what they can run. Firecracker has no PCI bus and therefore no GPU passthrough at all. Cloud Hypervisor does support VFIO passthrough, so this is a per-VMM design decision rather than an inherent limit of the approach [3].
Limited live migration
Traditional hypervisors have long supported migrating a running VM between hosts with no downtime. The earliest microVM VMMs lacked this entirely. Firecracker later added snapshot and restore, which is useful but not equivalent to full live migration [15].
Substantial orchestration work
A VMM such as Firecracker is a building block, not a platform: there is no scheduler, image registry, or networking control plane. Getting a microVM running is straightforward. Running many thousands across a fleet, with per-tenant networking, placement, image distribution, and lifecycle management, is where the real engineering lies [2][12].
Less mature tooling
than decades-old hypervisor platforms or the container ecosystem, though this continues to improve.
Requires hardware virtualization
MicroVMs depend on CPU virtualization extensions being available and exposed to the host, which can be a problem in nested-virtualization environments, and ties implementations to particular architectures, mainly x86_64 and aarch64 today [16][17][18].
7. Existing MicroVM Solutions

Firecracker (AWS) is the project that popularized the term, built originally to power AWS Lambda and Fargate. It combines a minimal device model, virtio for all data path I/O (plus a couple of small legacy devices for console output and shutdown), direct kernel boot, a REST API over a Unix socket for control, and the jailer wrapper that confines each VMM instance with its own namespaces, cgroups, chroot, unprivileged user and seccomp filter. Later versions added snapshot and restore, allowing an already-booted microVM to be cloned rather than booted afresh [2][15].

Cloud Hypervisor (originally Intel-led, now a broader community project) shares building blocks with Firecracker through rust-vmm, a set of common Rust crates, including kvm-ioctls, vm-memory, and virtio device implementations, reused across several VMM projects [19]. It occupies a similar niche but with a wider feature set: VFIO (Virtual Function I/O) device passthrough, live migration, and support for confidential-computing hardware such as Intel TDX (Trust Domain Extensions) and AMD SEV (Secure Encrypted Virtualization). It is one of the pluggable backends for Kata Containers [3].

Kata Containers (OpenInfra Foundation) is not a VMM but an OCI-compatible container runtime: a drop-in replacement for runc that runs each container or pod inside a real virtual machine while still speaking the APIs that containerd, CRI-O and Kubernetes expect. Its VMM is pluggable (QEMU, Cloud Hypervisor, or Firecracker), so a Kata deployment is only using microVMs when configured with one of the latter two. It was born from the 2017 merger of Intel's Clear Containers [9] and Hyper.sh's runV [10], and remains the main route by which microVMs reach existing container ecosystems [12].

QEMU's microvm machine type offers a stripped-down profile (-M microvm) that drops most legacy PC emulation in favour of a minimal virtio-focused platform for faster boot. It is still QEMU underneath, however, so it does not carry the reduced-codebase security story of a purpose-built minimal VMM [1].

crosvm (Google, Rust) is the VMM behind ChromeOS and Android's Linux and Android VMs. It shares rust-vmm heritage with the projects above and pushes sandboxing furthest of any of them, running individual device backends in separate processes with their own seccomp policies, so compromising one backend does not yield the whole VMM [20].

libkrun (Red Hat) packages a VMM as a library rather than a standalone binary, letting a program be launched inside a lightweight KVM-isolated VM through a simple API call. It underlies krunvm and Podman's krun platform, and is notably used to give containers genuine Linux-kernel isolation when running on macOS, where it uses Apple's Hypervisor.framework rather than KVM [21].

Hyperlight (Microsoft) is a newer and more specialized project aimed at sub-millisecond, extremely lightweight micro-guest sandboxes for small units of code such as WebAssembly modules, pushing the minimalism of the Firecracker approach further still for a narrower use case [22].

gVisor (Google) is worth naming for contrast rather than inclusion. It is not a hardware-virtualized microVM: it is a userspace application kernel, called Sentry, that intercepts a container's system calls and reimplements much of the Linux syscall surface itself, interposing a software isolation layer without necessarily booting a separate guest kernel at all. It addresses the same problem, safer multi-tenant sandboxing, by a different mechanism, and is used in App Engine, Cloud Run and GKE Sandbox [23].

Finally, a related but distinct idea: unikernels such as IncludeOS, OSv and MirageOS. Where a microVM minimizes the VMM, a unikernel minimizes the guest, compiling an application together with only the library-OS components it needs into a single specialized kernel image with no general-purpose OS beneath it [24]. The two are complementary rather than competing. Because they minimize different layers, a unikernel could in principle run as the guest inside a microVM VMM such as Firecracker, combining both kinds of minimalism.

8. Conclusion

A microVM is a virtual machine, in the full sense described in Section 2: its guest runs inside hardware-enforced guest mode, and its memory is bounded by EPT/NPT, the same isolation boundary a traditional VM has. What differs is everything constructed on top of that boundary. By replacing full hardware emulation with a minimal, virtio-only device model and booting the guest kernel directly, a microVM preserves the isolation guarantee that made VMs the safe choice for untrusted, multi-tenant code, while approaching the boot time and density that made containers practical at scale. This combination is exactly what Section 3 described cloud providers needing, and the one Section 5's table sets side by side.

This does not make microVMs a universal replacement for either technology. Section 6 identified where this combination still incurs a cost: reduced device support, a heavier footprint than a plain container, and an ecosystem that remains less mature than either of the technologies it sits between. The appropriate choice remains workload-specific, and Section 7's overview of Firecracker, Cloud Hypervisor, Kata Containers, and the rest exists precisely because no single implementation fits every case.
