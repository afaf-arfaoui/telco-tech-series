Episode 02

MicroVMs in practice

Dr. Afaf Arfaoui · October 19, 2026

In episode 01 we saw that a microVM is a VM that keeps the isolation enforced by the hardware that a conventional VM offers, while getting rid of the legacy device emulation and the boot sequence that make VMs slow to start. This is exactly what we need for a Virtual Network Function (VNF) deployment. A VNF (in this case UPF) needs to be isolated from the host and from other processes sharing the machine. It also needs to spin up quickly when something fails, in case of replacement, or migration. MicroVMs satisfy both requirements at once. The goal of this series is to test them for such deployments, namely a VNF and an AI agent.

In this episode, we are going to build the foundation that the rest of the series runs on. We will have two Firecracker microVMs on a single host, connected to each other through a private network, with outbound access to the Internet. None of the microVMs will do anything useful just yet. Their purpose will arrive later: the first will become the host for the eUPF in episode 07 and the second runs the AI agent that monitors it in episode 08. By the end of this episode both microVMs will be running and able to reach each other.

Note that everything in this episode will be done by hand. In episode 03, we will hand this same deployment to an AI agent.

1. The architecture

The system comprises one physical host, two Firecracker microVMs, one Linux bridge, and two TAP interfaces, one per microVM. Figure 1 shows how they are connected.

Figure 1.Network architecture of the host and the two microVMs
Host physical interface

This is the host’s normal network interface connected to the local network or Internet. It is used only if outbound Internet access is enabled for the microVMs via NAT.

Linux bridge (br0)

The bridge is a software Layer-2 switch inside the host that will be given the address 172.16.0.1/24. It forwards frames between the two TAP interfaces and acts as the default gateway for both microVMs.

The outbound traffic is sent by the microVM to br0 as its gateway, the host’s routing stack then routes it out through the host physical interface, and NAT rewrites the source address on the way. That path requires two things configured on the host: IP forwarding enabled (net.ipv4.ip_forward=1), and a masquerade rule for the 172.16.0.0/24 subnet. Both are set up in section 6.

TAP interfaces (tap0, tap1)

These are virtual network interfaces on the host. One end attaches to the bridge, the other is where the VMM reads and writes the microVM’s traffic. We will create one for each microVM, tap0 for upf-uvm and tap1 for agent-uvm. They carry no address of their own.

MicroVMs (upf-uvm, agent-uvm)

upf-uvm runs the eUPF, the user plane function that will be deployed in episode 07. Its interface eth0 has the IP address 172.16.0.2/24 and the default gateway 172.16.0.1.

agent-uvm hosts the AI agent that operates and monitors the eUPF, deployed in episode 08. Its interface eth0 has the IP address 172.16.0.3/24 and the default gateway 172.16.0.1.

The upf-uvm carries most of the load. It gets 4 GiB of RAM, two vCPUs, and an 8 GB root disk. It uses the custom 6.18 kernel with BPF and BTF enabled, built in section 7. The agent microVM is much lighter since the Claude model runs in the cloud, so the microVM only makes API calls and watches the eUPF. It gets 2 GiB of RAM, two vCPUs, and a 6 GB root disk.

Together, the two microVMs use 6 GiB of the 32 GiB on this laptop and under a third of its 22 CPU threads. That leaves plenty of memory for the host OS. If your machine has less memory, start with smaller microVMs and increase the values only if they struggle. Keep at least a quarter of your host RAM free for the host OS.

3. Prerequisites

Firecracker runs microVMs on top of KVM, so the host has to meet a few requirements first. This step runs a short set of checks. If one fails, fix it before moving on, because the later steps assume everything passed.

Operating system, kernel, and architecture

We need to check the Linux distribution and version, which helps with problem reporting later if needed. We also need to check the kernel version, because Firecracker needs a host kernel of 5.10 or newer.

The officially supported versions can be found in its documentation[1], check the page for the release you plan to use.

host shell
# Show the Ubuntu version
lsb_release -ds
# Show the running kernel version
uname -r
Hardware virtualization

We introduced the VT-x feature in episode 01. Now we need to check if it is available. On Intel processors, Linux marks VT-x support as vmx, and the command below counts how many of your processor’s cores report it. This is a workaround: instead of asking the processor directly, the command reads the CPU flags that Linux exposes and counts them. If it returns any number above zero, the feature is there. A zero usually means the processor does not support it or it is turned off in your computer’s BIOS or UEFI settings. If you have an AMD processor, replace vmx with svm.

host shell
# Count the CPU threads that report Intel VT-x (vmx)
grep -c -w vmx /proc/cpuinfo
The KVM module

We also discussed KVM in episode 01. This command lists the kernel modules, and keeps only those with names starting with kvm. On an Intel machine you should see kvm and kvm_intel. On an AMD one you should see kvm and kvm_amd. If nothing appears, KVM is not active, and therefore Firecracker cannot start a microVM.

host shell
# List the loaded KVM kernel modules
lsmod | grep '^kvm'
Access to the KVM device

We checked that kvm module is active, now we need to check if the kvm device is accessible. In the commands below, the first one shows the KVM device file and who is allowed to use it. The second checks whether your own user can actually use it. If it says KVM: NOT accessible, add yourself to the kvm group with sudo usermod -aG kvm $USER, then reboot, because the change only applies to new sessions.

host shell
# Show the KVM device file and who may use it
ls -l /dev/kvm
# Check that this user can read and write the KVM device file
test -r /dev/kvm && test -w /dev/kvm && echo "KVM: accessible" || echo "KVM: NOT accessible"
Network uplink

We also need to collect some useful information about the network. The first command below lists the network interfaces, which gives us a baseline before we add any new ones. The second shows the default route, which names the interface your internet traffic uses. The network rules we set up later will send the microVMs’ traffic out through that interface.

host shell
# List the network interfaces in short form
ip -br link
# Show the default route and the uplink interface
ip route show default
Verifying if Firecracker has been previously installed

We install Firecracker in the next step. However, if a version already appears when you run the command below, it is probably left over from an earlier installation or attempt, and it could conflict with the one we are about to install. To remove an old copy, run the second command. It deletes only the files in /usr/local/bin.

host shell
# Check whether a Firecracker binary is already installed
command -v firecracker || echo "firecracker: not installed"
# Remove the old Firecracker and jailer binaries from /usr/local/bin
sudo rm -f /usr/local/bin/firecracker /usr/local/bin/jailer
What a healthy host looks like

When everything is fine, the output shows:

  • a supported distribution and kernel
  • an architecture of x86_64 or aarch64
  • a non-zero vmx or svm count
  • the KVM modules loaded
  • KVM is accessible
  • a default route
  • enough memory and disk for your planned microVMs
  • no Firecracker installed yet

This means the host is ready for the next step.

4. Installing Firecracker

Firecracker publishes ready-made binaries on its GitHub releases page[2]. The commands below find the latest release and download the version that matches your processor into ~/Desktop/microVMs/firecracker. We prefer to keep everything reachable from the Desktop, so the whole lab lives under ~/Desktop/microVMs: the Firecracker release goes into firecracker, and the kernel, root filesystem, and disk images go into kernel_rootfs:

host shell
# Store the processor type (x86_64 on most laptops)
ARCH="$(uname -m)"
# Store the address of the Firecracker releases page
release_url="https://github.com/firecracker-microvm/firecracker/releases"
# Find the newest release tag and stop if none is found
latest=$(basename "$(curl -fsSLI -o /dev/null -w '%{url_effective}' "${release_url}/latest")")
: "${latest:?Could not find the latest release. Check your internet connection and try again.}"
# Store the lab folder on the Desktop
MICROVMS="$HOME/Desktop/microVMs"
# Create the folder for the Firecracker release
mkdir -p "$MICROVMS/firecracker"
# Download the release archive and extract it into the folder
curl -fsSL "${release_url}/download/${latest}/firecracker-${latest}-${ARCH}.tgz" \
| tar -xz -C "$MICROVMS/firecracker"

The tarball contains the Firecracker binaries, which are named with the version and processor type. Two of them matter here:

  • firecracker is the VMM itself.
  • jailer is the extra security layer we mentioned in episode 01. It runs Firecracker inside Linux isolation features such as namespaces and cgroups, which keeps each microVM contained when several workloads share one host. It is recommended for production, but we will not use it.
5. Kernel and root filesystem
Downloading the kernel and root filesystem

A microVM needs two files before it can boot: a Linux kernel and a root filesystem. Firecracker expects the kernel as an uncompressed binary called vmlinux. The root filesystem holds the operating system the microVM runs. The Firecracker team publishes tested versions of both in an Amazon S3 bucket[1], and the commands below fetch the latest ones that match your processor.

host shell
# Store the lab folder on the Desktop
MICROVMS="$HOME/Desktop/microVMs"
# Store the folder for the kernel and the root filesystem
KR="$MICROVMS/kernel_rootfs"
# Create the kernel_rootfs folder if it does not exist
mkdir -p "$KR"
# Move into the kernel_rootfs folder for the downloads
cd "$KR"
# Store the processor type (x86_64 on most laptops)
ARCH="$(uname -m)"
# Store the address of the Firecracker CI bucket
S3="https://s3.amazonaws.com/spec.ccfc.min"

# Find the newest CI build folder in the bucket
CI_ARTIFACTS_PREFIX=$(curl -fsSL "$S3?list-type=2&prefix=firecracker-ci/&delimiter=/" \
    | grep -oP "(?<=<Prefix>)firecracker-ci/[0-9]{8}-[^/]+/(?=</Prefix>)" \
    | sort \
    | tail -1)

Next, we look up the name of the newest kernel file:

host shell
# Find the newest CI kernel and stop if none is found
kernel_s3_path=$(curl -fsSL "$S3?list-type=2&prefix=${CI_ARTIFACTS_PREFIX}${ARCH}/vmlinux-" \
    | grep -oP "(?<=<Key>)(${CI_ARTIFACTS_PREFIX}${ARCH}/vmlinux-[0-9]+\.[0-9]+\.[0-9]{1,3})(?=</Key>)" \
    | sort -V | tail -1)
: "${kernel_s3_path:?No kernel found in ${CI_ARTIFACTS_PREFIX}}"

And we download the kernel:

host shell
# Download the CI kernel
wget "https://s3.amazonaws.com/spec.ccfc.min/${kernel_s3_path}"

The root filesystem uses the same approach:

host shell
# Find the newest CI Ubuntu root filesystem and stop if none is found
rootfs_s3_path=$(curl -fsSL "$S3?list-type=2&prefix=${CI_ARTIFACTS_PREFIX}${ARCH}/ubuntu-" \
    | grep -oP "(?<=<Key>)(${CI_ARTIFACTS_PREFIX}${ARCH}/ubuntu-[0-9]+\.[0-9]+\.squashfs)(?=</Key>)" \
    | sort -V | tail -1)
: "${rootfs_s3_path:?No Ubuntu rootfs found in ${CI_ARTIFACTS_PREFIX}}"
# Read the Ubuntu version from the file name
ubuntu_version=$(basename "$rootfs_s3_path" .squashfs | grep -oE '[0-9]+\.[0-9]+')
# Download the root filesystem under a name that includes its version
wget -O "ubuntu-$ubuntu_version.squashfs.upstream" "https://s3.amazonaws.com/spec.ccfc.min/$rootfs_s3_path"

The Ubuntu file is a squashfs image, which is a compressed, read-only format. We want a writable root filesystem, so we convert it to ext4 in section 7.

When this step finishes, you should have a vmlinux-* file and an ubuntu-*.squashfs.upstream file in ~/Desktop/microVMs/kernel_rootfs.

Note: This is the Firecracker CI kernel. CI stands for continuous integration, the automated builds Firecracker runs to test its microVMs. Both microVMs boot it, but this kernel does not enable BPF tracing or BTF, which the eUPF needs. Section 7 explains how to get a kernel that does.

6. Networking

In this section we set up the host side of the lab network. We first create the bridge and the TAP devices, then add the NAT rules that let the microVMs reach the Internet. Nothing is connected yet: the microVMs attach to these interfaces when they start in section 7.

Creating the bridge and the TAP devices

The first commands remove any leftover devices from an earlier attempt, so you can run the block again without errors. Then they create br0, give it the gateway address, and create one TAP device per microVM, attached to the bridge.

host shell
# Name of the bridge
BR_DEV="br0"
# Gateway address of the bridge, used by both microVMs
BR_IP="172.16.0.1/24"
# Name of the TAP device for upf-uvm
TAP_UPF="tap0"
# Name of the TAP device for agent-uvm
TAP_AGENT="tap1"

# Remove an old upf-uvm TAP device if one exists
sudo ip link del "$TAP_UPF" 2>/dev/null || true
# Remove an old agent-uvm TAP device if one exists
sudo ip link del "$TAP_AGENT" 2>/dev/null || true
# Remove an old bridge if one exists
sudo ip link del "$BR_DEV" 2>/dev/null || true

# Create the bridge
sudo ip link add name "$BR_DEV" type bridge
# Give the bridge its gateway address
sudo ip addr add "$BR_IP" dev "$BR_DEV"
# Switch the bridge on
sudo ip link set dev "$BR_DEV" up

# Create both TAP devices and attach them to the bridge
for TAP in "$TAP_UPF" "$TAP_AGENT"; do
# Create a TAP device
  sudo ip tuntap add dev "$TAP" mode tap
# Switch the TAP device on
  sudo ip link set dev "$TAP" up
# Attach the TAP device to the bridge
  sudo ip link set dev "$TAP" master "$BR_DEV"
# End of the loop
done

# Check that the bridge and both TAP devices exist
ip -br link | grep -E 'br0|tap0|tap1'

In the output, the words inside the brackets are the interface flags. UP means the interface is switched on. state DOWN means no link is detected, and NO-CARRIER means nothing is connected at the other end yet. That is normal before a microVM attaches to the interface.

Enabling NAT for the microVM subnet

The microVMs reach the Internet through the host. Each laptop names its network interface differently, so the command below asks the system which interface carries Internet traffic instead of making you look up the name.

host shell
# Store the name of the uplink interface
HOST_IFACE=$(ip route show default | awk '/default/ {print $5; exit}')
# Show the uplink name
echo "Uplink: $HOST_IFACE"

# Let the host forward packets between interfaces
sudo sysctl -w net.ipv4.ip_forward=1
# Rewrite the source address of microVM traffic that leaves through the uplink
sudo iptables -t nat -A POSTROUTING -s 172.16.0.0/24 -o "$HOST_IFACE" -j MASQUERADE
# Allow traffic from the bridge out through the uplink
sudo iptables -A FORWARD -i br0 -o "$HOST_IFACE" -j ACCEPT
# Allow replies to connections that a microVM started
sudo iptables -A FORWARD -i "$HOST_IFACE" -o br0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

The first rule turns the host into a router. The MASQUERADE rule rewrites the private source addresses to the host's own address, so replies find their way back to the right microVM. The two FORWARD rules let traffic pass between the bridge and the uplink, and allow replies to connections that started inside.

Note: Ubuntu's firewall tool, ufw, can set the FORWARD policy to DROP, which blocks these rules. If the microVMs cannot reach the Internet in section 8, check the policy with sudo iptables -S FORWARD.

The IP forwarding setting and the iptables rules do not survive a reboot. We will put them in a script when we automate the deployment.

7. Launching the first microVM

The first microVM, upf-uvm, runs the eUPF. It uses the root filesystem downloaded in section 5. The eUPF needs Linux 5.15 or newer with BPF tracing and BTF enabled, and the Firecracker CI kernel does not enable either. So upf-uvm first boots the CI kernel. We need that boot to read the running config, which the new kernel starts from, so the new kernel keeps every option that already boots this microVM. A generic Linux kernel may lack the drivers this microVM needs, so we start from a config known to boot it.

Preparing the upf-uvm disk

The CI root filesystem is a read-only SquashFS image with no SSH keys. Firecracker needs an ext4 image, so we unpack the SquashFS, install a public key for SSH, and pack the result into an 8 GB ext4 file. The file is sparse, so it only uses host disk space as data is written.

host shell
# Store the lab folder on the Desktop
MICROVMS="$HOME/Desktop/microVMs"
# Store the folder for the kernel and the root filesystem
KR="$MICROVMS/kernel_rootfs"

# Unpack the Ubuntu root filesystem into a normal folder
sudo unsquashfs -d "$KR/squashfs-upf" "$(ls "$KR"/ubuntu-*.squashfs.upstream | tail -1)"

# Create an SSH key pair for logging in to the image
ssh-keygen -t ed25519 -f "$KR/upf-uvm-key" -N ""

# Install the public key where the SSH server looks for it
sudo mkdir -p "$KR/squashfs-upf/root/.ssh"
# Copy the public key into the upf-uvm image
sudo cp "$KR/upf-uvm-key.pub" "$KR/squashfs-upf/root/.ssh/authorized_keys"
# Restrict the .ssh folder to its owner
sudo chmod 700 "$KR/squashfs-upf/root/.ssh"
# Restrict the authorized keys file to its owner
sudo chmod 600 "$KR/squashfs-upf/root/.ssh/authorized_keys"
# Remove the DNS settings that come with the image
sudo rm -f "$KR/squashfs-upf/etc/resolv.conf"
# Write public DNS servers into the image
printf "nameserver 1.1.1.1\nnameserver 8.8.8.8\n" | sudo tee "$KR/squashfs-upf/etc/resolv.conf" >/dev/null

# Create an 8 GB sparse file and fill it with the folder contents as an ext4 filesystem
truncate -s 8G "$KR/upf-uvm.ext4"
# Fill the file with the folder contents as an ext4 filesystem
sudo mkfs.ext4 -d "$KR/squashfs-upf" -F "$KR/upf-uvm.ext4"
Starting the Firecracker process for upf-uvm

Each microVM needs its own Firecracker process. Open a new terminal, which we call upf-uvm, and keep it open. Once the microVM boots, this terminal shows its console output.

host shell
# Store the lab folder on the Desktop
MICROVMS="$HOME/Desktop/microVMs"
# Remove the socket left by an earlier run
sudo rm -f /tmp/firecracker-upf.socket

# Find the Firecracker binary extracted in section 4
FC_BIN=$(ls "$MICROVMS"/firecracker/release-*/firecracker-*-$(uname -m) | tail -1)

# Start the Firecracker process, which creates the socket
sudo "$FC_BIN" --api-sock /tmp/firecracker-upf.socket
Configuring upf-uvm

The commands below run in another terminal, which we call upf-uvm-settings. They send settings to the Firecracker process in upf-uvm through its socket. The eUPF gets 2 vCPUs and 4 GiB of RAM. Setting smt to false turns off simultaneous multithreading (Intel calls it Hyper-Threading) for this microVM, so each vCPU runs on a whole physical core. Firecracker cannot add vCPUs to a running microVM, so the heavy-load tests described in section 2 will need a restart with a higher count.

host shell
# Store the lab folder on the Desktop
MICROVMS="$HOME/Desktop/microVMs"
# Store the folder for the kernel and the root filesystem
KR="$MICROVMS/kernel_rootfs"
# Variables used by the commands below
API_SOCKET_UPF="/tmp/firecracker-upf.socket"
# CI kernel for the first boot
KERNEL="$(ls "$KR"/vmlinux-* | grep -v btf | tail -1)"
# Kernel arguments for upf-uvm, including its address
KERNEL_BOOT_ARGS="console=ttyS0 reboot=k panic=1 pci=off ip=172.16.0.2::172.16.0.1:255.255.255.0::eth0:off:1.1.1.1:8.8.8.8"
# The root disk of upf-uvm
ROOTFS_UPF="$KR/upf-uvm.ext4"
# MAC address for the upf-uvm network interface
FC_MAC_UPF="06:00:AC:10:00:02"

# Log file for Firecracker
sudo curl -X PUT --unix-socket "$API_SOCKET_UPF" \
  --data "{\"log_path\": \"$KR/firecracker-upf.log\", \"level\": \"Debug\", \"show_level\": true, \"show_log_origin\": true}" \
  http://localhost/logger

# Two vCPUs and 4 GiB of RAM, with SMT off
sudo curl -X PUT --unix-socket "$API_SOCKET_UPF" \
  --data '{"vcpu_count": 2, "mem_size_mib": 4096, "smt": false}' \
  http://localhost/machine-config

# Kernel to boot
sudo curl -X PUT --unix-socket "$API_SOCKET_UPF" \
  --data "{\"kernel_image_path\": \"${KERNEL}\", \"boot_args\": \"${KERNEL_BOOT_ARGS}\"}" \
  http://localhost/boot-source

# Root disk built above
sudo curl -X PUT --unix-socket "$API_SOCKET_UPF" \
  --data "{\"drive_id\": \"rootfs\", \"path_on_host\": \"${ROOTFS_UPF}\", \"is_root_device\": true, \"is_read_only\": false}" \
  http://localhost/drives/rootfs

# Network interface connected to tap0
sudo curl -X PUT --unix-socket "$API_SOCKET_UPF" \
  --data "{\"iface_id\": \"net1\", \"guest_mac\": \"${FC_MAC_UPF}\", \"host_dev_name\": \"tap0\"}" \
  http://localhost/network-interfaces/net1

# Wait briefly, then boot the microVM
sleep 0.015
# Start upf-uvm
sudo curl -X PUT --unix-socket "$API_SOCKET_UPF" \
  --data '{"action_type": "InstanceStart"}' \
  http://localhost/actions

The IP address comes from the ip= argument in the boot arguments, so the kernel configures eth0 before the system starts and no manual step is needed. The MAC address only has to be unique on the bridge. Its last four bytes, AC:10:00:02, are the IP address in hexadecimal: AC is 172, 10 is 16, 00 is 0, and 02 is 2, which gives 172.16.0.2. The other arguments follow the getting-started guide[1].

Checking the network of upf-uvm

The console of upf-uvm is already open in its terminal, so you can run the commands below. If you need another session, log in from a different terminal with this command:

host shell
# Log in to upf-uvm from the host with its key
ssh -i ~/Desktop/microVMs/kernel_rootfs/upf-uvm-key root@172.16.0.2

Then run these checks inside upf-uvm. They confirm that the boot arguments set the address on eth0, the default route, and the DNS servers:

guest shell (upf-uvm)
# Show the address of eth0
ip -br addr show eth0
# Show the default route and the uplink interface
ip route show default
# Show the DNS servers in use
cat /etc/resolv.conf

The CI startup script also adds a second address, 172.16.0.2/30, to eth0. A /30 mask covers only two usable addresses, so it conflicts with the /24 subnet from the boot arguments and can make the rest of the bridge unreachable, so we need to remove it:

guest shell (upf-uvm)
# Remove the extra /30 address
ip addr del 172.16.0.2/30 dev eth0
Building the kernel for the eUPF

The eUPF needs a kernel with BPF tracing and BTF enabled, and the CI kernel has neither. We will build that kernel now, starting from the config of the running upf-uvm. That is why upf-uvm first boots on the CI kernel. The new file is named vmlinux-*-btf, where the * stands for the kernel version. The -btf part means the kernel has BTF (BPF Type Format), the kernel type information that eBPF tools read. We will explain some basics of eBPF in episode 05.

You can skip the build by downloading the kernel we built [3], saving it in kernel_rootfs as vmlinux-6.18-btf, and continuing with the restart step below. To build it yourself, check the Further details section below and run its steps on your host. Both options give the same file.

The eUPF loads small programs into the kernel, and those programs need a tracing helper called bpf_trace_printk. The CI kernel does not include it, so the eUPF fails to load. The build below turns on the missing options. You do not need to understand eBPF yet: we explain the basics in episode 05 and the eUPF itself in episode 06. For now, just follow the steps.

The build starts from the config of the running upf-uvm, so the new kernel keeps every option that already boots this microVM. The config comes from 6.18.56, and the source is the newest 6.18 release, so olddefconfig fills in the options that the newer source added.

Run the steps in order on your host. Step 3 needs upf-uvm running.

Install the build tools on the host:

host shell
# Refresh the package list
sudo apt update
# Install the compiler and the tools needed to build a kernel
sudo apt install -y build-essential flex bison libelf-dev libssl-dev bc dwarves curl xz-utils

Download the newest 6.18 kernel source:

host shell
# Move to the lab folder
cd ~/Desktop/microVMs
# Find the newest 6.18 release file name on kernel.org
LATEST=$(curl -s https://cdn.kernel.org/pub/linux/kernel/v6.x/ | grep -o 'linux-6\.18\.[0-9]*\.tar\.xz' | sort -V | uniq | tail -1)
# Show the file name that was found
echo "$LATEST"
# Download the newest 6.18 source archive
curl -fLO "https://cdn.kernel.org/pub/linux/kernel/v6.x/$LATEST"
# Extract the source archive
tar xf "$LATEST"

Copy the running config from upf-uvm, which must be running on the CI kernel:

host shell
# Store the path of the extracted source folder
SRC=$(ls -d ~/Desktop/microVMs/linux-6.18.* | sort -V | tail -1)
# Show the source folder, to check it
echo "$SRC"
# Copy the config of the running upf-uvm kernel into the source folder, only if the copy works (upf-uvm must be running)
ssh -i ~/Desktop/microVMs/kernel_rootfs/upf-uvm-key -o StrictHostKeyChecking=accept-new root@172.16.0.2 'zcat /proc/config.gz' > "$SRC/.config.tmp" && mv "$SRC/.config.tmp" "$SRC/.config"
# Check the number of lines, which should be around 3900
wc -l "$SRC/.config"

Enable the eBPF and tracing options, then check them:

host shell
# Store the path of the extracted source folder
SRC=$(ls -d ~/Desktop/microVMs/linux-6.18.* | sort -V | tail -1)
# Move into the kernel source folder
cd "$SRC"
# Turn on the eBPF and tracing options
scripts/config --disable DEBUG_INFO_NONE --enable BPF --enable BPF_SYSCALL --enable BPF_JIT --enable BPF_EVENTS --enable KPROBES --enable KPROBE_EVENTS --enable FTRACE --enable TRACING --enable PERF_EVENTS --enable XDP_SOCKETS --enable CGROUP_BPF --enable DEBUG_INFO --enable DEBUG_INFO_DWARF5 --enable DEBUG_INFO_BTF
# Fill in the options that the newer source added
make olddefconfig
# Check that the key options are set to y
grep -E '^CONFIG_(BPF_SYSCALL|BPF_EVENTS|DEBUG_INFO_BTF)=' .config

Build the kernel:

host shell
# Store the path of the extracted source folder
SRC=$(ls -d ~/Desktop/microVMs/linux-6.18.* | sort -V | tail -1)
# Move into the kernel source folder
cd "$SRC"
# Build the kernel image
make -j"$(nproc)" vmlinux

Copy the kernel into the kernel_rootfs folder:

host shell
# Store the path of the extracted source folder
SRC=$(ls -d ~/Desktop/microVMs/linux-6.18.* | sort -V | tail -1)
# Copy the built kernel into kernel_rootfs
cp "$SRC/vmlinux" ~/Desktop/microVMs/kernel_rootfs/vmlinux-6.18-btf
# Check that the file exists
ls -lh ~/Desktop/microVMs/kernel_rootfs/vmlinux-6.18-btf
Restarting upf-uvm with the eUPF kernel

Stop upf-uvm first.

Then change the KERNEL line of the configuration block in Configuring upf-uvm from this:

second terminal
# CI kernel for the first boot
KERNEL="$(ls "$KR"/vmlinux-* | grep -v btf | tail -1)"

to this:

second terminal
# The kernel built for upf-uvm
KERNEL="$KR/vmlinux-6.18-btf"

Start the process again with the command in Starting the Firecracker process for upf-uvm, and run the configuration block again. Only the kernel line changes. agent-uvm keeps the CI kernel, since it does not need BPF tracing.

In the upf-uvm terminal, check that the new kernel runs with BTF:

guest shell (upf-uvm)
# Show the running kernel version
uname -r
# Check that the BTF file exists
ls -l /sys/kernel/btf/vmlinux

The BTF file must exist. If it does not, the microVM still runs the CI kernel, so check the KERNEL line and restart again.

8. A second microVM and connectivity

The second microVM, agent-uvm, will run the AI agent that monitors the eUPF. It is built the same way as upf-uvm, with its own disk, key, socket, and TAP device. The agent is lighter, so it gets 2 vCPUs and 2 GiB of RAM.

Preparing the agent-uvm disk

Build the agent-uvm disk the same way as upf-uvm: unpack the same Ubuntu root filesystem into its own folder, add a new SSH key, and pack the result into a 6 GB ext4 file named agent-uvm.ext4. The commands below repeat the upf-uvm steps with agent-uvm names and a 6 GB size.

host shell
# Store the lab folder on the Desktop
MICROVMS="$HOME/Desktop/microVMs"
# Store the folder for the kernel and the root filesystem
KR="$MICROVMS/kernel_rootfs"

# Unpack the Ubuntu root filesystem into a normal folder
sudo unsquashfs -d "$KR/squashfs-agent" "$(ls "$KR"/ubuntu-*.squashfs.upstream | tail -1)"

# Create an SSH key pair for logging in to the image
ssh-keygen -t ed25519 -f "$KR/agent-uvm-key" -N ""

# Install the public key where the SSH server looks for it
sudo mkdir -p "$KR/squashfs-agent/root/.ssh"
# Copy the public key into the agent-uvm image
sudo cp "$KR/agent-uvm-key.pub" "$KR/squashfs-agent/root/.ssh/authorized_keys"
# Restrict the .ssh folder to its owner
sudo chmod 700 "$KR/squashfs-agent/root/.ssh"
# Restrict the authorized keys file to its owner
sudo chmod 600 "$KR/squashfs-agent/root/.ssh/authorized_keys"
# Remove the DNS settings that come with the image
sudo rm -f "$KR/squashfs-agent/etc/resolv.conf"
# Write public DNS servers into the image
printf "nameserver 1.1.1.1\nnameserver 8.8.8.8\n" | sudo tee "$KR/squashfs-agent/etc/resolv.conf" >/dev/null

# Create a 6 GB sparse file and fill it with the folder contents as an ext4 filesystem
truncate -s 6G "$KR/agent-uvm.ext4"
# Fill the file with the folder contents as an ext4 filesystem
sudo mkfs.ext4 -d "$KR/squashfs-agent" -F "$KR/agent-uvm.ext4"
Starting the Firecracker process for agent-uvm

Open a new terminal, which we call agent-uvm, and keep it open. The boot arguments differ from upf-uvm because they contain the address of agent-uvm, 172.16.0.3. The first two lines of the command below set them in this terminal.

host shell
# Store the lab folder on the Desktop
MICROVMS="$HOME/Desktop/microVMs"
# Store the folder for the kernel and the root filesystem
KR="$MICROVMS/kernel_rootfs"
# Variables for the agent-uvm boot
KERNEL="$(ls "$KR"/vmlinux-* | grep -v btf | tail -1)"
# Kernel arguments for agent-uvm, including its address
KERNEL_BOOT_ARGS="console=ttyS0 reboot=k panic=1 pci=off ip=172.16.0.3::172.16.0.1:255.255.255.0::eth0:off:1.1.1.1:8.8.8.8"

# Remove the socket left by an earlier run
sudo rm -f /tmp/firecracker-agent.socket

# Find the Firecracker binary extracted in section 4
FC_BIN=$(ls "$MICROVMS"/firecracker/release-*/firecracker-*-$(uname -m) | tail -1)

# Start the Firecracker process, which creates the socket
sudo "$FC_BIN" --api-sock /tmp/firecracker-agent.socket
Configuring agent-uvm

Run these in another terminal, which we call agent-uvm-config. The commands are the same as for upf-uvm, with the agent's values: 2 vCPUs, 2 GiB of RAM, its own disk, MAC address, and TAP device. The first line sets the boot arguments that contain the address 172.16.0.3.

host shell
# Store the lab folder on the Desktop
MICROVMS="$HOME/Desktop/microVMs"
# Store the folder for the kernel and the root filesystem
KR="$MICROVMS/kernel_rootfs"
# CI kernel for the first boot
KERNEL="$(ls "$KR"/vmlinux-* | grep -v btf | tail -1)"
# Variables used by the commands below
KERNEL_BOOT_ARGS="console=ttyS0 reboot=k panic=1 pci=off ip=172.16.0.3::172.16.0.1:255.255.255.0::eth0:off:1.1.1.1:8.8.8.8"
# Control socket of agent-uvm
API_SOCKET_AGENT="/tmp/firecracker-agent.socket"
# The root disk of agent-uvm
ROOTFS_AGENT="$KR/agent-uvm.ext4"
# MAC address for the agent-uvm network interface
FC_MAC_AGENT="06:00:AC:10:00:03"

# Log file for Firecracker
sudo curl -X PUT --unix-socket "$API_SOCKET_AGENT" \
  --data "{\"log_path\": \"$KR/firecracker-agent.log\", \"level\": \"Debug\", \"show_level\": true, \"show_log_origin\": true}" \
  http://localhost/logger

# Two vCPUs and 2 GiB of RAM, with SMT off
sudo curl -X PUT --unix-socket "$API_SOCKET_AGENT" \
  --data '{"vcpu_count": 2, "mem_size_mib": 2048, "smt": false}' \
  http://localhost/machine-config

# Kernel to boot
sudo curl -X PUT --unix-socket "$API_SOCKET_AGENT" \
  --data "{\"kernel_image_path\": \"${KERNEL}\", \"boot_args\": \"${KERNEL_BOOT_ARGS}\"}" \
  http://localhost/boot-source

# Root disk for agent-uvm
sudo curl -X PUT --unix-socket "$API_SOCKET_AGENT" \
  --data "{\"drive_id\": \"rootfs\", \"path_on_host\": \"${ROOTFS_AGENT}\", \"is_root_device\": true, \"is_read_only\": false}" \
  http://localhost/drives/rootfs

# Network interface connected to tap1
sudo curl -X PUT --unix-socket "$API_SOCKET_AGENT" \
  --data "{\"iface_id\": \"net1\", \"guest_mac\": \"${FC_MAC_AGENT}\", \"host_dev_name\": \"tap1\"}" \
  http://localhost/network-interfaces/net1

# Wait briefly, then boot the microVM
sleep 0.015
# Start agent-uvm
sudo curl -X PUT --unix-socket "$API_SOCKET_AGENT" \
  --data '{"action_type": "InstanceStart"}' \
  http://localhost/actions
Checking the network of agent-uvm

The console of agent-uvm is already open in its terminal. Run the commands below. They are the same checks as for upf-uvm, and they confirm the address, the default route, and the DNS servers set by the boot arguments:

guest shell (agent-uvm)
# Show the address of eth0
ip -br addr show eth0
# Show the default route and the uplink interface
ip route show default
# Show the DNS servers in use
cat /etc/resolv.conf

The CI startup script also adds 172.16.0.3/30 to eth0, for the same reason as on upf-uvm, so we need to remove it:

guest shell (agent-uvm)
# Remove the extra /30 address
ip addr del 172.16.0.3/30 dev eth0
Testing connectivity

From agent-uvm, run the commands below. Each one checks a different part of the network: the bridge, the other microVM, the Internet by address, and DNS.

guest shell (agent-uvm)
# Check the bridge gateway
ping -c 2 172.16.0.1
# Check upf-uvm
ping -c 2 172.16.0.2
# Check the Internet by address
ping -c 2 1.1.1.1
# Check DNS and the Internet by name
ping -c 2 google.com
# Check that package downloads work through NAT
apt update

From upf-uvm, check that it reaches the agent with ping -c 2 172.16.0.3.

If agent-uvm reaches upf-uvm but not the Internet, the problem is on the host. Check these host settings: IP forwarding, the NAT rule, and the FORWARD policy. The commands below show each one. If the host reaches the Internet but a microVM does not, the cause is usually the guest's default route or DNS.

host shell
# Check that IP forwarding is on (1 means on)
cat /proc/sys/net/ipv4/ip_forward
# Show the NAT rule for the microVM subnet
sudo iptables -t nat -L POSTROUTING -n -v
# Show the FORWARD policy and rules
sudo iptables -S FORWARD
9. Conclusion

We now have two microVMs running on a private bridge: upf-uvm, which will run the eUPF, and agent-uvm, which will monitor it. Both can reach each other and the Internet.
